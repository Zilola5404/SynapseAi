# Project Rules — Конституция проекта

> Обязательный документ. Соблюдение — не рекомендация, а требование для всех ИИ и людей.
> Обновляет: только Owner (Project Owner), по явному решению.
> Когда обновляется: крайне редко, любое изменение фиксируется в `templates/decision.md`.
> Используют: все роли, все ИИ.
> Обязателен: да, приоритет выше любого другого документа кроме прямого указания Owner.

---

## Статья 1. Главный принцип

Каждый исполнитель перед передачей результата должен быть уверен, что выполнил
свою работу максимально качественно. Если есть сомнения — задача считается
незавершённой.

**Исполнитель имеет право завершить задачу только после того, как сам убедился,
что результат соответствует требованиям. Запрещается перекладывать ответственность
за проверку своей работы на следующий этап.** Формальное прохождение своего этапа
без внутренней уверенности в качестве результата приравнивается к невыполненной
задаче, даже если формальные чек-листы отмечены.

Основная цель проекта — не скорость разработки, а стабильный, понятный и
качественный продукт, готовый к эксплуатации и дальнейшему развитию.

## Статья 2. Самопроверка исполнителя

После выполнения задачи запрещается сразу передавать её следующему исполнителю.
Обязательная минимальная последовательность перед передачей:

1. Проверить отсутствие ошибок.
2. Проверить сборку проекта.
3. Проверить, что изменённый функционал работает.
4. Проверить, что не сломаны связанные функции.
5. Выполнить доступные тесты.
6. Исправить найденные проблемы.
7. Только после успешной проверки передать задачу дальше через `HANDOFF_PROTOCOL.md`.

## Статья 3. «Не передавать с известными ошибками»

Если исполнитель обнаружил ошибку в своей работе — он обязан исправить её сам.
Запрещены формулировки при передаче:
«пусть QA проверит», «следующий исправит», «возможно работает», «не проверял»,
«должно работать».

QA проверяет качество продукта, а не выполняет работу разработчика за него.

## Статья 4. Обязательное тестирование после изменений

Объём проверки соответствует объёму изменений: запуск приложения, сборка,
unit-тесты, integration-тесты, smoke-тесты, проверка API, ручная проверка
изменённого сценария. Если тест невозможно выполнить — исполнитель обязан
явно указать причину в отчёте о передаче.

## Статья 5. Ответственность по ролям

| Роль | Отвечает за |
|---|---|
| Architect | архитектурную корректность решений |
| Developer | качественную реализацию согласно спецификации |
| Reviewer | инженерное качество кода |
| Auditor | независимую проверку, не связанную с автором изменений |
| QA | подтверждение работоспособности с точки зрения пользователя |
| Documentation | актуальность документации на момент завершения задачи |
| Project Manager | соответствие ТЗ, срокам и приоритетам |
| Release Manager | безопасность и корректность выпуска |

Никто не должен рассчитывать, что следующий этап исправит его ошибки.

## Статья 6. Права доступа к файлам

| Роль | Может изменять | Не может изменять |
|---|---|---|
| Product Owner | `PROJECT_RULES.md`, приоритеты в `DASHBOARD.md` | код |
| Project Manager | `CURRENT_STATUS.md`, `DASHBOARD.md`, `templates/sprint.md`, `templates/task.md` | `PROJECT_RULES.md`, production-конфигурацию |
| Chief Architect | `/specifications`, `AI_CONTEXT.md` (раздел архитектуры) | код без согласования с Developer |
| Senior Developer | `/src`, связанные тесты, `templates/task.md` (свой статус) | `PROJECT_RULES.md`, `/reports` аудита |
| Reviewer | комментарии в `templates/code_review.md` | код напрямую (только через PR) |
| Independent Auditor | `templates/audit.md`, `reports/risk_*.md`, `reports/tech_debt_*.md` | код, чужие отчёты задним числом |
| QA Lead | `templates/qa_report.md`, `/tests` | продовую конфигурацию |
| Technical Writer | `/docs`, `/specifications` (описательная часть) | код, архитектурные решения |
| Release Manager | `/releases`, `CHANGELOG` | код в момент релиза без Hotfix-процедуры |
| Control Center | `/ai/DASHBOARD.md` (агрегация), маршрутизация задач | содержательные решения ролей |

Любое изменение файла вне зоны ответственности роли — нарушение конституции
проекта и должно быть отклонено на этапе Review/Audit.

## Статья 7. Язык

- Вся документация (`/docs`, `/reports`, `/templates`, `/checklists`, `/ai`, описательная часть `/prompts`) — только на русском языке.
- Английский допускается только для: исходного кода, названий классов/функций/методов/переменных, API, SQL, команд терминала, Docker, Git, названий технологий.
- Commit-сообщения — только на русском языке, простыми и понятными формулировками, чтобы смысл был понятен даже через несколько месяцев. Подробности — `GIT_WORKFLOW.md`.

## Статья 8. Definition of Done — обязательность

Задача не считается завершённой, пока не выполнены критерии из
`DEFINITION_OF_DONE.md`. Ссылка на выполненные критерии обязательна в отчёте
о передаче.

## Статья 9. Эскалация

Если исполнитель не может выполнить требование конституции (недостаточно
данных, конфликт приоритетов, техническое ограничение) — задача не передаётся
молча, а эскалируется Project Manager с явным описанием причины в
`CURRENT_STATUS.md`, раздел «Известные проблемы / блокеры».

## Статья 10. Приоритет документов при противоречии

2. `PROJECT_RULES.md`
3. `AI_CONTEXT.md`
4. `DEFINITION_OF_DONE.md`
5. Промпт конкретной роли
6. Шаблоны и чек-листы
